
# me: терминал, в котором уютно

Долгое время мой терминал напоминал мастерскую, где инструменты свалены в одну кучу, а половину из них уже не вспомнишь зачем брал. В `.bashrc` копились алиасы — я добавлял их, забывал, добавлял снова. Одни конфликтовали с другими, третьи не работали после обновления системы, четвёртые просто молча игнорировались в скриптах. Чтобы прибавить яркость экрана, я каждый раз гуглил busctl — и каждый раз удивлялся, что не могу запомнить эту строку. Я перепробовал разные способы навести порядок: писал отдельные скрипты, раскладывал по папкам, вешал на хоткеи — всё это жило своей жизнью, не имело единой документации и не поддавалось контролю.

Мне нужен был не очередной лаунчер и не менеджер команд. Мне нужен был пульт. Как в старом магнитофоне: видишь все кнопки, нажимаешь — работает. Который можно взять с собой на другую машину, который не сломается от одной неверной строчки, и в котором каждая кнопка сама рассказывает, что делает.

Так появился me.

## Что болит в алиасах из .bashrc

Для меня алиас — это крючок, на который я вешаю команду. Удобно — пока крючков пять. А когда их тридцать, они начинают выпадать: один не туда забили, второй отвалился после обновления, третий просто молча конфликтует с четвёртым. И главное — в скриптах этих крючков вообще нет. Вот что я вынес из долгой жизни с .bashrc:

| Проблема | Почему это больно |
| --- | --- |
| **Не работают в скриптах** | Bash-скрипты не видят алиасы без `shopt -s expand_aliases` (который никто не ставит). Скрипт с алиасами упадет на другой машине — будете искать, почему. |
| **Нет документации** | Через месяц не помнишь, что делает `alias rd='rm -rf'`, а что `alias rd='rdesktop'`. Начинается `grep alias ~/.bashrc` — и так каждый раз. |
| **Аргументы только в конец** | `alias backup='tar -czf'` — передать путь в середину нельзя. Нужна функция, но в .bashrc это ещё одна свалка. |
| **Нет проверок** | Алиас не проверяет, установлена ли утилита. Не обрабатывает ошибки. Не возвращает код возврата. |
| **Нет изоляции** | Все алиасы в одной куче. Переменные, export-ы, кастомные функции — перемешано. Контроль версий? Руками вырезать из .bashrc. |
| **Конфликты имён** | Два алиаса с одинаковым именем — молча побеждает последний. Диагностики нет. |
| **Только для ручного ввода** | Нельзя вызвать из скрипта, нельзя передать по fifo, нельзя привязать к хоткею в i3 как надёжную команду. |

## Что предлагает me

`me` родился как реестр всего, что я делаю в терминале. Это bash-скрипт (`~/.local/bin/me`) + конфиг (`~/.config/me/me.conf`). В конфиге описываются методы с мета-тегами. Вызываются через `me <глагол>`.

**Архитектура — три слоя:**

```
терминал / скрипт / хоткей
        │
        ▼
  me (bash-движок)
        │
        ▼
  me.conf (реестр методов)
        │
        ├── me_method_play()    — встроенный метод
        ├── me_method_upgrade() — встроенный метод
        └── me_lib/ff.sh        — внешний скрипт-метод
```

**[SCREENSHOT: architecture.png]**
*Схема: на входе `me <глагол>`, движок ищет метод в me.conf через awk, проверяет `bash -n`, при ошибке — предупреждение, остальные методы не страдают.*

> *Мысль вслух: я специально сделал так, чтобы движок не грузил всё подряд. Потому что сам же обламывался, когда один сломанный .bashrc ронял весь шелл. Здесь — если один метод упал, остальные работают. Мне это кажется правильным.*

### Как это выглядит на практике

Я люблю слушать музыку через mpv в фоне. Раньше, чтобы поставить на паузу, я лез в терминал и набирал busctl с километровым путем — это было безумие. Сейчас я просто жму `me pause` или, если руки заняты, переключаю через горячую клавишу, которая вызывает `me toggle`. То же самое с яркостью:

Было:
```bash
busctl --user call org.xfce.PowerManager \
  /org/xfce/PowerManager \
  org.xfce.Power.Backlight IncreaseBrightness
```

Стало:
```bash
me bright up
```

Разница не в том что второй вариант короче, а что у него есть:
- **Документация:** `me -m bright` покажет описание и пример
- **Автокомплит:** Tab подставит `bright`, Tab ещё раз — `up`/`down`
- **Уведомление:** после изменения яркости — notify-send
- **Fallback:** если XFCE не работает — пробует GNOME
- **Интерактив:** `me int` → fzf → выбор → команда в истории bash (жми ↑)

> *Мысль вслух: честно говоря, я перестал запоминать названия методов. Когда печатаю `me int`, вижу список и просто выбираю. Как быстрый запуск в телефоне — только в терминале.*

## Как устроен метод формально

Каждый метод — обычная bash-функция с мета-тегами перед ней:

```bash
#@method: pause
#@description: Поставить плеер на паузу
#@example: me pause
me_method_pause() {
    playerctl pause 2>/dev/null || true
}
```

Движок **не грузит все методы сразу**. При запуске `me` импортирует только хелперы (общие функции без префикса `me_method_`). Когда вызывается конкретный метод — движок:

1. **Находит** функцию `me_method_<имя>()` в `me.conf` через awk
2. **Проверяет** синтаксис через `bash -n /dev/shm/me_check_XXXXXX.sh`
3. **eval + кэш** в `/dev/shm/me_$USER/me.cache` с автоинвалидацией по md5

Если метод упал с синтаксической ошибкой — он просто не загрузится, остальные методы продолжат работать.

> *Мысль вслух: этот механизм — моя гордость. me никогда не упадет целиком из-за одной опечатки. Он скажет: «вот тут ошибка, иди смотри». И я иду. И исправляю. Без страха, что рассыплется всё.*

```bash
#@method: press
#@description: Комбинация клавиш через xdotool
#@example: me press ctrl+shift+t
me_method_press() {
    [ -z "$1" ] && { echo "Укажи комбинацию: me press ctrl+t"; return 1; }
    xdotool key "$1"
}
```

Этот метод можно:
- Вызвать вручную: `me press ctrl+shift+t`
- Использовать в скрипте: `if me press ctrl+alt+F2; then echo "терминал открыт"; fi`
- Привязать к хоткею i3/sway: `bindsym $mod+t exec me press ctrl+shift+t`
- Зашерить: `me share press` → `tar.gz` в `import/`

## Чего нет у алиасов

Без me ты пишешь:

```bash
yt-dlp --default-search "ytsearch10:${*:1}" --get-title --get-id --no-warnings 2>/dev/null | \
  paste - - | fzf --reverse | cut -f2 | \
  xargs -I {} mpv --no-video "https://youtube.com/watch?v={}"
```

С me это:

```bash
me smy "led zeppelin kashmir"
```

Не потому что me умный. А потому что `smy` — метод в ме библиотеке `me_lib/smy.sh`, в котором вся логика вынесена в отдельный скрипт с проверками:

- проверка yt-dlp и mpv перед запуском
- поиск 20 результатов → fzf → выбор
- воспроизведение в mpv

**Алиасы не могут:**
- Проверить, установлен ли ffmpeg/yt-dlp/mpv перед вызовом
- Вернуть код возврата и обработать ошибку
- Вызваться из скрипта (sh/ash/dash — алиасов нет)
- Иметь внутренние переменные и аргументы в середине строки
- Иметь автокомплит с описанием

**me может — и это не магия, а bash.** Когда я писал me, я сознательно не добавлял никаких языков, фреймворков, менеджеров зависимостей. Метод — это bash-функция, и всё. Я хотел, чтобы любой, кто знает bash, мог открыть me.conf и сразу понять, что там написано, и при необходимости — исправить.

## Что даёт переезд с алиасов на me

### 1. Централизованное управление

Вместо 50 строк в `.bashrc` — один файл `~/.config/me/me.conf`. Его можно положить в git, диффить, откатывать. Звучит банально, но когда я впервые сделал `git diff me.conf` и увидел, что изменил в методах за месяц — я понял, что обратно к .bashrc уже не вернусь.

### 2. Документирование по факту

Мета-теги `#@description:` и `#@example:` пишутся один раз — при создании метода. Через месяц `me` покажет справку, через год — тоже.

### 3. Скриптовая совместимость

`me pause` работает внутри bash-скрипта, в `cron`, в `systemd --user`, в keybinding оконного менеджера. Ты не привязан к интерактивному режиму.

### 4. Работа в любом контексте — без потери окружения

Одна из частых проблем при переносе скриптов в `/usr/local/bin` — потеря переменных окружения. Скрипт, запущенный как отдельный процесс, не наследует `DISPLAY`, `DBUS_SESSION_BUS_ADDRESS`, `PULSE_SERVER` и другие переменные, определённые в интерактивном сеансе. Это приводит к тому, что команды для уведомлений, управления яркостью или звуком перестают работать.

Традиционное решение — вручную экспортировать нужные переменные в начале скрипта или создавать алиасы, но алиасы не работают в неинтерактивных оболочках.

`me` решает эту проблему иначе. Метод `me` выполняется в контексте текущей оболочки — он загружается через `source` (или eval) и наследует все переменные окружения родительского процесса. Таким образом, вызов `me bright up` или `me say` работает всегда, независимо от того, откуда он вызван: из терминала, из скрипта, из горячей клавиши или из `cron`, если указан полный путь к `me` и окружение передано корректно.

На практике это означает, что метод, написанный однажды, не требует правок при переносе на другую машину или в другую среду. Это снижает количество «магических» ошибок, связанных с окружением, и делает `me` надёжным инструментом для автоматизации.

И еще важный момент прямо аргумент аргумент в пользу  me


 Портативность без привязки к .bashrc

На разных Linux-машинах файл `.bashrc` часто сильно отличается: в одном дистрибутиве он загружает `bash_completion`, в другом — `profile.d`, в третьем — кастомные переменные для GUI. Вычленять алиасы из этого зоопарка и переносить их на новую систему — муторно и чревато конфликтами.

`me` решает это кардинально: все методы живут в отдельном файле `~/.config/me/me.conf`, который не зависит от настроек оболочки. Для переноса на другую машину достаточно скопировать этот файл и установить `me` (или просто скопировать весь каталог `~/.local/bin/me/`). Никаких правок в `.bashrc` не требуется — `me` работает как отдельный исполняемый файл в `PATH`.

Это делает `me` идеальным инструментом для работы на разных системах: от минималистичных live-образов до полных десктопных окружений. Один и тот же набор методов работает везде одинаково.

---


### 5. Изоляция ошибок

Метод с синтаксической ошибкой не ломает пульт. Ошибка — предупреждение в stderr. Движок продолжает работу.

### 6. Расширяемость без коллизий

Новый метод = 5 строк в `me.conf`. Имя уникально в пределах конфига. Никаких конфликтов с export-ами и source-ми.

### 7. Интерактивный выбор

`me int` → fzf со списком методов, preview, пример. Выбрал — команда в историю. Я перестал запоминать имена. Когда хочешь сделать паузу, а метод называется `pause`, это просто. Но когда их тридцать — проще выбрать глазами, чем вспоминать.

### 8. Социальное — share/import

Когда я переносил me на новую машину, я понял: копировать me.conf — это полдела, а зависимости? А скрипты из me_lib? Поэтому я сделал share/import.

```
me share gifx   # → ~/.local/bin/me/import/gifx.tar.gz
me import gifx  # → разархивирует, добавит метод в me.conf, скопирует библиотеки
```

Внутри архива — метод, зависимости (скрипты из `me_lib/`, конфиги) и `install.sh`, который делает всё автоматически. Можно загрузить с pastebin — `me import https://...` — и метод появится на чистой системе. Я не называю это «социальной сетью для geek-ов» — это просто возможность не переписывать одно и то же дважды.

### 9. Кэширование в ОЗУ

Кэш методов лежит в `/dev/shm/me_$USER/` — RAM-диск. Хеш `me.conf` сравнивается при каждом вызове. Если конфиг не менялся — загрузка из памяти. Если изменился — пересборка.

## Версионирование файлов с cit

Помимо вызова готовых методов, `me` предоставляет инструмент для лёгкого версионирования файлов — `cit`. Это не замена Git, а способ сохранять состояния файлов прямо в процессе работы, без инициализации репозитория и коммитов.

`cit` хранит снепшоты (слепки) файлов в скрытой папке `.cit/` рядом с проектом. Каждый снепшот содержит копию файла и комментарий — ченджлог. Формат имени: `имя_файла__дд-мм-гггг_чч-мм-сс.cit`.

Основные операции:

- **Создать снепшот (Push)** — выбрать файлы или папки через `fzf`, ввести комментарий. Снепшот сохраняется с меткой времени. Если файл содержит shebang (`#!`), комментарий автоматически вставляется в его заголовок.
- **Откат к предыдущей версии** — текущий файл заменяется последним снепшотом из `.cit/`. Предыдущее состояние не сохраняется — чтобы его зафиксировать, нужно заранее сделать снепшот вручную.
- **Выбор версии для восстановления** — через `fzf` показываются все снепшоты с их ченджлогами. Выбранный снепшот копируется поверх текущего файла.
- **Удаление в корзину** — снепшот перемещается в `.cit/tr_cit/` с сохранением структуры путей. Это позволяет не удалять версии безвозвратно.
- **Восстановление из корзины** — список удалённых снепшотов с возможностью вернуть их обратно в основное хранилище.
- **Очистка корзины** — полностью удаляет все снепшоты из `.cit/tr_cit/`.

**Флаг `-f` (finalize)** — сборка полного ченджлога из всех снепшотов. Все комментарии собираются в один блок, который вставляется в тело основного файла (после shebang). Одновременно создаётся копия с суффиксом `-F` и отдельный лог-файл с историей всех версий. Этот режим удобен для фиксации релизной версии скрипта.

Все операции доступны через интерактивное меню `cit` или через `me cit` (если метод зарегистрирован).

## me create — генерация нового метода (скоро)

Часто спрашивают: «а как быстро добавить новый метод?». Писать вручную блок в `me.conf` — 30 секунд, но можно быстрее.

**`me create <имя>`** будет делать так:

1. Спрашивает: описание, пример, внутренний или внешний скрипт
2. Генерирует блок с мета-тегами и шаблоном функции
3. Вставляет в `me.conf` (в алфавитном порядке или в указанную позицию)
4. Если метод использует внешний скрипт — создаёт заготовку в `me_lib/`
5. Проверяет синтаксис готового конфига

```
$ me create docker-ps
  Имя: docker-ps
  Описание: Список запущенных Docker-контейнеров
  Пример: me docker-ps
  Тип: [внутренний] внешний

  #@method: docker-ps
  #@description: Список запущенных Docker-контейнеров
  #@example: me docker-ps
  me_method_docker-ps() {
      docker ps --format "table {{.Names}}\t{{.Status}}\t{{.Ports}}"
  }

  Добавить в me.conf? [Y/n]
```

## Масштабирование на парк машин

`me` изначально задумывался как инструмент для одной машины, но архитектура позволяет масштабировать его на парк машин без переписывания кода.

**Экспорт и импорт методов** — ключевой механизм для этого.

- `me share <имя_метода>` — упаковывает метод, его мета-теги и все зависимости (скрипты из `me_lib/`, конфиги) в один архив `tar.gz` в папке `~/.local/bin/me/import/`. Внутри архива лежит `install.sh`, который автоматически регистрирует метод в `me.conf` и копирует файлы в нужные места.
- `me import <имя_метода>` или `me import ./pkg.tar.gz` или `me import https://...` — устанавливает метод на текущую машину. Если метод уже существует — запрашивается подтверждение на замену.

**Сценарий для парка машин:**

1. На мастер-машине создаётся набор методов.
2. Для каждого метода выполняется `me share` — получается архив.
3. Архивы распространяются по локальной сети (через общую папку, `scp`, `rsync` или HTTP).
4. На каждой целевой машине выполняется `me import` с указанием пути или URL.

Таким образом, администратор может за несколько минут развернуть единый набор команд на десятках серверов. При этом каждый администратор может дополнять `me.conf` локально — личные методы не конфликтуют с общими, потому что `me` загружает методы из одного конфига, а имена уникальны.

## Цифры

- **me (движок):** 244 строки bash
- **me.conf (реестр):** 416 строк, ~30 методов
- **Зависимости:** bash 4.0+, fzf, playerctl, ripgrep, ffmpeg (опционально)
- **Установка:** `bash install_me.sh` → PATH, комплишн, me.conf
- **Время загрузки пустого me:** ~0.02 сек (кэш в /dev/shm)
- **Время первого вызова метода:** ~0.05 сек (bash -n + eval)
- **Занимаемое место:** < 150 КБ весь проект с библиотеками

## Почему это просто инструмент

В me нет:
- Менеджеров зависимостей
- Языков кроме bash
- Конфигурационных формалов (yaml/toml/json)
- Плагинов (метод == bash-функция)
- ORM, DI, middleware и прочего

В me есть:
- awk, который выкусывает блок из конфига
- `bash -n`, который проверяет синтаксис
- `/dev/shm` для кэша
- md5sum для автоинвалидации

Всё. Именно поэтому это работает — нет прослойки между тобой и терминалом.

## Когда не нужно

me не делает:
- Не заменяет man/info — сложные тулы читают через свои доки
- Не автоматизирует то, что делаешь раз в год
- Не превращает терминал в GUI

Если у тебя 3 алиаса и они работают — me не нужен. Если ты тратишь время на то, чтобы вспомнить/нагуглить/написать команду, которую используешь ежедневно — me может убрать этот шаг.

## Попробуй

Сейчас я не представляю свою работу без me. Он стал моим вторым языком для терминала. Если ты чувствуешь такую же боль — попробуй.

Установка занимает 5 минут:

```bash
bash ~/.local/bin/me/install_me.sh
source ~/.profile
me
```

Создай один метод — для playerctl, для яркости, для чего угодно. Открой `~/.config/me/me.conf`, добавь пять строк:

```bash
#@method: hello
#@description: Моя первая команда
#@example: me hello
me_method_hello() {
    echo "Привет, терминал!"
}
```

Вызови: `me hello`. Если что-то пойдёт не так — движок скажет где, и не сломает ничего остального.

В терминале станет уютно. Не магически, а просто — потому что команды, которые ты используешь каждый день, лежат на видном месте и сами рассказывают, что делают. Как пульт от старого магнитофона.
